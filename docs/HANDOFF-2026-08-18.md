## 3. Recovery and safety machinery (do not fight it)
- gx10-4 runs `gx10-sentinel.service`: relaunches production through the guarded wrapper if the API
  is down. It respects the flock. To do fleet work: hold the lock first:
  `ssh gx10-1 'nohup flock /var/tmp/glm_launch.lock sleep 21600 >/dev/null 2>&1 &'` and release with
  `pkill -f "^flock /var/tmp/glm_launch.lock"`.
- Node protection on all four (`node_protect.sh` in spark-fleet-guard): SBSA hardware watchdog daemon,
  LOAD-ONLY test (ping test rebooted a healthy node; min-memory test false-fired; both removed),
  earlyoom installed but DISABLED (it killed a healthy boot during graph capture), sshd/dockerd
  OOMScoreAdjust -1000, plymouth-quit-wait masked, persistent rails + mgmt NM profile.
- ncclras client at /var/tmp/ncclras on all nodes; `wedge_capture.sh` (fleet-guard) samples RAS
  collective counts twice 95 s apart to discriminate a frozen livelock from a real divergence.
- Mac-side gx10 watchdog (~/.gx10-watchdog) is NOT loaded (launchctl bootstrap needs a GUI login);
  the sentinel covers recovery.
- Rules paid for in outages (see kit docs/SESSION-2026-08-17.md and fleet-guard README):
  1. First boot of any new code at 32K context, never at 316K.
  2. Never a bulk transfer or docker save on a node during a boot (page cache counts against vLLM's
     free-memory check on unified memory). Drop caches before every launch.
  3. Never two loads at once (98 GB x2 = power cycle). The flock exists for this.
  4. Memory margin: production leaves ~700 MB available + 3-4 GB swap, PSI 0. Anything heavier than the
     production identity (e.g., NVFP4 107 GB/rank + MTP) tips all four nodes into unified-memory thrash
     and needs a physical power cycle. It happened 2026-08-17 ~22:44 UTC.
  5. Evict the old checkpoint BEFORE restoring another (disk-full at 33% cost an hour on 08-18).
  6. Verify checkpoints as SETS of (name,size) not sorted listings (mac vs linux sort differ).
  7. Launch workers first (reverse rank), head last; `--cpu-distributed-timeout-seconds 1800`;
     `--disable-custom-all-reduce` (else a 300 s init stall).

## 5. The decode-step profile (the most important new data)
Traces: /private/tmp/claude-502/-Users-gigachad-Desktop-File-Dump/4b2e7a10-461a-49ad-9aeb-e2205483e3ea/scratchpad/profiles/gx10-{1..4}/
(8 files, 127 MB; C4_C1_* = C1 window, C4_* = C4 window). Analyzer: kit benchmarks/profile/analyze_trace.py.
Doc: kit docs/DECODE_STEP_PROFILE-2026-08-18.md (with a dated correction).
- Step: ~110-130 ms at C1, ~200 ms at C4 (38 and 46 steps in the windows; agrees with tok/s).
- Per layer (C4, from the kernel sequence): AllReduce ~60 us -> norm -> marlin::Marlin (w8a16 dense
  q/kv proj) -> b12x indexer path with TWO AllGather_RING_LL (~85 us each) -> mgUnifiedPrefill (sparse
  MLA decode, ~38 us) -> DCP a2a pack + SendRecv (~50 us) + unpack -> o_proj -> AllReduce ~60 us -> norm ->
  router/topk -> marlin_moe w13 (~890 us) -> silu -> marlin_moe w2 (~450 us) -> moe_sum -> shared expert.
- Shares (all four ranks within 1%): expert MoE GEMMs + dense w8a16 Marlin 57-58%; NCCL all-reduce
  10-11%; NCCL all-gather + send/recv 15%; dense GEMMs (cutlass wmma bf16, gemvx) 8%; sparse attention 4%;
  norm/elementwise 4%; sampler/MTP <1%. GPU busy 97% (C4) / 92% (C1). Idle 3-8%.
- Byte floor: per touched expert per rank ~4.85 MB (6144x2048 w13+w2, int4 g128, TP-sharded); C1
  (3 tokens, ~23 distinct experts/layer) => marlin_moe measured ~0.53 ms/layer vs ~0.41 ms floor =
  ~77% of 273 GB/s. The expert path is close to bandwidth-bound. FIRST version of my reading said
  "launch-bound, 3-6x off": WRONG, corrected in the doc.
- Not yet checked: whether the dense w8a16 Marlin linears (8-20% of the step depending on batch) hit
  the byte floor at M=3..12; whether the C4 window's expert overlap (same prompt x4) understates bytes.
